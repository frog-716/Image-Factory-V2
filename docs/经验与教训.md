# 经验与教训

## 1. V1 的核心问题是验证顺序错了

V1 太早投入 Workflow、Runtime、Runner、审核、恢复和自动合成。

这些可靠性能力并非没有价值，问题在于：

> 先把“怎么稳定自动跑”做复杂了，后面才验证“创作方法是否能稳定得到可交付图片”。

自动化只能放大一个已经成立的方法；方法不成立时，自动化只会更快、更稳定地产出低质量结果。

## 2. Codex 的角色要分清

V1 把 Codex 放进日常必经的生图生产链后，真实产出质量不理想，也很难发挥网页 GPT 连续交互修改的优势。

不能简单归因为“Codex 生图能力差”。影响结果的因素包括：

- Prompt 路线不成熟；
- 商品素材与角度不足；
- 自动流程对创意约束过强；
- 早期背景生成 + 商品硬合成路线错误；
- 工程执行与审美判断本来就是不同类型的工作。

最终结论：

> **Codex 作为开发和维护引擎很有价值；但把它作为当前业务量下的一线日常生图主引擎，在本项目实际试验中效果不佳。**

## 3. 生成模型不能补商品事实

没有鞋底、后跟、背面等真实素材时，模型生成出的合理细节也只能算猜测。

## 4. 数据表不是产品界面

六张底表可以是正确的数据模型，但一线运营日常只应该看到“准备生图”和“回来选图”。

## 5. 技术测试通过不等于业务通过

附件往返、哈希一致、单测通过，只能证明对应工程能力。
最后仍然要看：图片能不能用、运营是否看得懂、返工是否减少。

## 6. 面试与作品集的事实边界

我最重要的一次产品纠偏，是发现自己把“生产系统的可靠性”做在了“创作方法成立”之前。后来保留了值得复用的可靠性经验，推翻重型生图流水线，让Codex回到开发维护角色，让运营用更适合连续创作的网页GPT完成实际生图。

这是基于本项目试验条件的角色选择，不是对某个模型能力的普遍判决。不能把原型完成、测试通过或个别采用结果写成规模上线、转化率改善或成本节省。内部经验包已整理为当前能力、历史试错和面试表达三个层次，重复补丁集中，原始心得与历史资料保留；公开文档不携带客户细节。完整操作与原理见[项目手册](完整使用与原理手册.md)。
